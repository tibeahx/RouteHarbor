# Подготовка домашнего стенда

Основной роутер — Xiaomi AX3200. Модель второго устройства пока неизвестна.
Ни на одном физическом устройстве OpenRHP ещё не проверен. Этот гайд подготавливает
стенд; он не является инструкцией по прошивке роутера.

## Сначала — без изменения действующей сети

1. Посмотрите наклейку второго роутера: точная модель и аппаратная ревизия.
   Пароли, серийный номер и MAC публиковать не нужно. Запишите текущую прошивку обоих
   устройств в их административной панели.
2. Проверьте, работает ли уже OpenWrt. Если осталась заводская прошивка, установка
   OpenWrt — отдельный подготовленный процесс для конкретной модели, с проверкой
   загрузчика и способа восстановления. OpenRHP этого не делает. Документация
   [OpenWrt для AX3200](https://openwrt.org/toh/xiaomi/ax3200) — исходная точка, а не
   разрешение выполнять команды другой аппаратной ревизии.
3. Подготовьте Ethernet-кабель и компьютер с работающим проводным доступом к LAN.
   Wi-Fi — целевой backhaul, но провод нужен как независимый путь восстановления.
   Оставьте основной домашний интернет работающим до проверки отдельного стенда.
4. Сохраните конфигурации, список пакетов и способ входа локально. WAN/PPPoE-данные
   храните в закрытом файле, не в чате. Копия настроек не равна полному flash dump.
5. Для уже работающего OpenWrt используйте имеющуюся SSH-конфигурацию и ключ.
   Не выключайте проверку host key. Изменившийся fingerprint сначала объясните.

## Что передать для следующего этапа

Достаточно точной модели/ревизии второго роутера, версий прошивки, подтверждения
проводного доступа и адресов/SSH-алиасов разрешённых тестовых устройств. Данные
доступа передавайте через существующий защищённый канал или локальный файл.
Агент сам получит capabilities, интерфейсы и ресурсы — переписывать их вручную не надо.

## Уже доступный виртуальный стенд

На компьютере с Docker из корня проекта:

```sh
sh scripts/lab-paths.sh
sh scripts/lab-network.sh
```

Первый проверяет независимые direct, два настоящих nfqws-профиля и CONNECT-прокси.
Второй применяет правила самого OpenRHP, проверяет маршруты/DNS и убивает helper,
чтобы проверить самостоятельный откат. Контейнеры не используют host network и не
трогают роутеры. Эти проверки не подтверждают procd/netifd/fw4 или радиодрайверы.

Отдельно доступен [стенд пакетов и служб OpenWrt](evidence/openwrt-sdk.md):
`scripts/lab-openwrt.py` устанавливает настоящие SDK-пакеты через opkg и проверяет
procd/netifd/fw4, права процессов, API-транзакции и защищённое удаление в контейнере
с OpenWrt userland. Проверенные входные архивы и команды подготовки приведены в
связанном отчёте. Контейнер использует ядро Docker Linux; это не полная загрузка
OpenWrt, проверка ABI модулей, радио или физических роутеров.

## Приёмка на OpenWrt

Сначала установите пакет на изолированную совместимую OpenWrt, оставив routing off.
Выполните [FOR_AGENTS](../FOR_AGENTS.md), затем проверьте с отдельного LAN-клиента:

- DNS, TCP, UDP/QUIC и выбранную политику IPv6; доступ к панели и локальным сервисам.
- Раздельные отказы внешнего выхода: полный, частичный, задержка, ограничение скорости.
- Остановку движка, helper и API во время apply; отсутствие незапрошенного direct.
- Перезапуск firewall, смену WAN, reboot и восстановление после обновления.
- WAN packet capture: защищаемые DNS/TCP/UDP/IPv6 не выходят вне разрешённого пути.

Сначала второй узел подключается по Ethernet: один DHCP, отсутствие NAT/собственного
RA, видимость каждого клиента на gateway. Затем проверяется разрешённый обоими
радиодрайверами Wi-Fi-режим с шифрованием. Не соединяйте два активных uplink одновременно.
Неизвестный «repeater»/«mesh» на заводской прошивке не подтверждает совместимость.

Плохой Wi-Fi uplink должен отображаться как проблема покрытия, а не вызывать смену
VPN. Успех фиксируется отдельно для каждого устройства, режима, версии OpenWrt,
ядра и пакетов. Не переключайте всю домашнюю сеть до этих проверок.
